Permissions

WeMessage asks macOS for exactly two things, and it will tell you which one is missing rather than failing silently. One of the two comes back every time you update, and that is worth reading before it happens.

Full Disk Access

What it grants

Read access to chat.db, the local iMessage database already sitting on your Mac. WeMessage opens it read-only and in immutable mode, which is how every iMessage tool on macOS works.

Why it is needed

There is no macOS API for reading your message history. The database is the only source, and macOS puts it behind Full Disk Access.

What is never done with it

Nothing is written to Apple's database, ever. Nothing read out of it is uploaded. The gateway reads, matches your rules, and hands the match to the agent you chose.

Automation, for Messages

What it grants

Permission for the daemon to tell Messages to send a message you have already approved.

Why it is needed

This is the single seam in the product where text can leave your Mac as an iMessage, and the kill switch sits directly on it. One seam is the design: the suite asserts that outbound sending is reachable from exactly one call site and that the call site requires an approved draft.

You can skip it

Read-only mode runs with no Automation grant at all. Agents still draft, you still triage, and nothing can be sent because nothing is wired to send it.

Every update re-locks Full Disk Access

This is the real cost of an unsigned build, and it is not the Gatekeeper prompt. macOS identifies an unsigned app by a hash of its binary, and that hash changes on every build. So after every update the WeMessage row in Privacy and Security, Full Disk Access stays visibly switched on while the gateway's reads of the message database start failing. Nothing is broken and no data is lost. The switch is telling you about an app that no longer exists at that hash.

Re-granting it takes four moves:

  1. Open System Settings, Privacy and Security, Full Disk Access.
  2. Select the WeMessage entry and remove it with the minus button.
  3. Add /Applications/WeMessage.app back with the plus button.
  4. Restart the gateway with wemessaged service restart, or quit and reopen the app.

Toggling the switch off and on does not work. Removing the entry and adding it back is the fix, and it is not the same operation. The entry the switch belongs to points at a build that is gone, so flipping it re-authorises the wrong binary, twice. This is the step people skip, and skipping it is why the app looks broken after an update when it is not.

wemessage doctor reports this exact case by name rather than leaving you to guess at it, and the onboarding wizard checks the daemon's own reads instead of trusting what the switch says.

Checking the grants

One command reports the state of each permission, what is missing, and the exact remediation, and exits non-zero while anything is unresolved:

wemessage doctor

The onboarding wizard runs the same checks with the same words, so the GUI and the terminal cannot tell you two different stories.

What is never asked for

No Contacts grant, no Accessibility grant, no network permission beyond a listener bound to your own machine, and no account anywhere. WeMessage has no cloud relay, no analytics, and no background uploads. The only text that ever leaves your Mac is what you route to an agent, and if that agent runs on this machine, nothing leaves at all.
